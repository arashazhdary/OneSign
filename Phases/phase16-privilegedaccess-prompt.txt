Step 3: JITGrant entity and integration with AccessRequests
--------------------------------------------------

1) Create JITGrant entity

- In an appropriate module (e.g. Authorization.PrivilegedAccess):

  - Properties:
    - Id (Guid)
    - TenantId (Guid)
    - UserId (Guid)
    - RoleId (Guid)
    - GrantedAt (DateTimeOffset)
    - ExpiresAt (DateTimeOffset)
    - ApprovedByUserId (Guid)
    - RequestId (Guid) (AccessRequestItem Id)
    - Status (Active, Expired, Revoked)

- Add EF mapping:
  - Table: e.g. PrivilegedJITGrants
  - Indices:
    - TenantId + UserId + Status
    - TenantId + ExpiresAt

2) Extend AccessRequests domain (Phase 12)

- Add TargetType = PrivilegedRole in AccessRequestItem enum.
- Add field:
  - DurationRequestedMinutes (int?).
- Validation for privileged requests:
  - DurationRequestedMinutes must be within allowed bounds for that role:
    - e.g. per-role configuration or safe defaults:
      - min 15 minutes, max 8 hours (you define realistic numbers using config).
  - Justification MUST be non-empty.

3) Service to create JIT grants on approval

- Implement service, e.g. `IPrivilegedAccessService`:

  - `Task<JitGrant> CreateJitGrantForApprovedRequestAsync(AccessRequestItem item, Guid approverUserId)`

- Behavior:
  - Validate that AccessRequestItem.TargetType == PrivilegedRole.
  - Resolve role, ensure IsPrivileged = true.
  - Compute ExpiresAt = now + DurationRequestedMinutes.
  - Create JITGrant:
    - Status = Active
  - Call Authorization/Role service:
    - assign the privileged role to the user in this tenant.
  - Audit:
    - "PrivilegedAccess.JITGranted" with:
      - TenantId, UserId, RoleId, GrantedAt, ExpiresAt, RequestId, ApprovedByUserId.

- Wire this service into AccessRequests approval flow:
  - When an AccessRequestItem of type PrivilegedRole transitions to Approved:
    - call CreateJitGrantForApprovedRequestAsync.

--------------------------------------------------
Step 4: JIT expiry worker
--------------------------------------------------

Implement a background worker/hosted service:

- Periodic task, e.g. every minute or configurable.
- Queries JITGrant table for:
  - Status = Active
  - ExpiresAt <= now.

For each expired JITGrant:

- Use PrivilegedAccessService:
  - `ExpireJitGrantAsync(jitGrantId)` which must:
    - Call Authorization/Role service to remove the privileged role from the user.
    - Set JITGrant.Status = Expired.
    - Set ExpiresAt (already set), update LastUpdated/ProcessedAt if you track it.
    - Audit:
      - "PrivilegedAccess.JITExpired" with full context.

- Ensure:
  - Idempotency: expiring an already Expired/Revoked JITGrant does nothing.
  - Errors are logged and captured via Observability.

Add metrics:
- Number of active JIT grants.
- Number of expired JIT grants processed.
- Any failures when expiring.

Step 5: BreakGlass account model and login flow
--------------------------------------------------

1) BreakGlassAccount entity

- Entity with:
  - Id (Guid)
  - Username (string, unique)
  - IsEnabled (bool)
  - AllowedTenants (could be:
    - a join table BreakGlassAllowedTenant: BreakGlassAccountId, TenantId
    - or a JSON list if your shared pattern uses it)
  - AllowedRoles (similar: join table to RoleId)
  - LastUsedAt (DateTimeOffset?)

- EF configuration and migration.

2) BreakGlass management APIs

- In Security or Global admin API:

  - `GET /api/security/breakglass-accounts`
  - `POST /api/security/breakglass-accounts`
  - `PUT /api/security/breakglass-accounts/{id}`
  - `DELETE /api/security/breakglass-accounts/{id}` (soft disable)

- Only GlobalAdmin/SecurityOfficer can manage these.

3) BreakGlass authentication flow

- Implement a special login path, e.g. `/auth/breakglass`.
- Authentication for BreakGlass MUST NOT piggyback on normal user DB lightly:
  - Use dedicated credentials (e.g. hashed password in secure store) or configured secrets.
  - At minimum, use strong hashing and NIST compliant password policies.

Behavior on login:

- Validate:
  - Account exists, IsEnabled = true.
- Evaluate:
  - Identify target Tenant (may be explicitly chosen, or limited by AllowedTenants).
- For allowed tenant:
  - Issue a session and tokens with high privileges according to AllowedRoles:
    - Use Authorization/Role assignment in a time-bound or session-bound manner.
- Force strong MFA if integrated with any factor provider (if available).
- Log audit event:
  - "PrivilegedAccess.BreakGlassLogin":
    - BreakGlassAccountId, Username
    - TenantId
    - IP address, UserAgent
    - Justification text and Incident/Ticket id (if required).
- Trigger Notification:
  - Use NotificationCenter:
    - send immediate alerts to SecurityOfficer / GlobalAdmin group.

4) BreakGlass usage policy

- On login request, require:
  - Justification text
  - Optional: external Incident ticket id
- This is captured in audit logs.

3) API for revoking privileged sessions

- Endpoint:
  - `POST /api/tenant/security/privileged-sessions/{sessionId}/revoke`

    - revoke tokens (access/refresh)
  - Audit:
    - "PrivilegedAccess.SessionRevokedByAdmin":
