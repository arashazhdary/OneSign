Step 4: Core services – Template, Router, Outbox, Sender
--------------------------------------------------

Implement INotificationTemplateService

- Methods:
  - GetTemplatesAsync(tenantId)
  - GetTemplateAsync(tenantId, templateId)
  - CreateTemplateAsync(tenantId, CreateNotificationTemplateRequest)
  - UpdateTemplateAsync(tenantId, templateId, UpdateNotificationTemplateRequest)
  - DeleteTemplateAsync(tenantId, templateId)

Behavior:
- When resolving template for a given (tenantId, eventType, language):
  - If there is a tenant-specific template → use it.
  - Otherwise fall back to global template (TenantId = Guid.Empty).
  - If language-specific localization does not exist:
    - Fall back to default language (e.g., "en").

Implement INotificationRouter

Define a context type, e.g.:

- `NotificationEventContext`:
  - TenantId
  - EventType
  - Recipients: list of RecipientInfo (userId, displayName, email, phone, preferredLanguage).
  - Payload: strongly-typed object or generic dictionary with event data:
    - ip, location, device, app, etc depending on event.

Method:

- `Task RouteAsync(NotificationEventContext context)`

Behavior:

1) For each recipient:
   - Load NotificationEventSubscription for (tenant, eventType).
   - Load user NotificationPreference (from Phase 9) if exists.
   - Combine:
     - Tenant default channels (DefaultChannels).
     - User preference.
     - If OverrideUserPreference is true:
       - enforce tenant channels (ignore user preference).
     - Else:
       - intersection or combination according to Phase 11 spec:
         - at minimum: do not send on channels user has disabled.

2) For each (recipient, channel) combination to be sent:
   - Resolve language:
     - Use recipient.PreferredLanguage if set.
     - Else tenant default or global default.
   - Resolve template based on (tenant, eventType, language):
     - Use INotificationTemplateService described above.
   - Render payload:
     - Replace placeholders in Subject/Body with context.Payload and recipient data.
   - Create NotificationOutboxItem with:
     - Status = Pending.
     - Priority:
       - Critical for security events (new login, suspicious login, MFA changes).
       - High for governance SoD violations, access review assignment.
       - Normal for most other events.

3) Persist all outbox items using INotificationOutboxService.

Implement INotificationOutboxService

- Methods:
  - EnqueueAsync(NotificationOutboxItem item)
  - GetPendingBatchAsync(int batchSize, NotificationPriority minPriority)
  - UpdateStatusAsync(itemId, newStatus, retryCount, timestamps, providerResponseCode/message)

Implement INotificationSenderService and channel senders

INotificationSenderService:

- `Task ProcessPendingAsync(int batchSize)`:
  - Load pending items ordered by:
    - Priority (Critical → Low).
    - CreatedAt.
  - For each item:
    - Set Status = Sending.
    - Call appropriate channel sender:
      - IChannelEmailSender.SendAsync(outboxItem)
      - IChannelSmsSender.SendAsync(outboxItem)
      - IChannelInAppSender.SendAsync(outboxItem)
      - IChannelWebhookSender.SendAsync(outboxItem)
    - On success:
      - Set Status = Sent, SentAt = now.
      - Create NotificationDeliveryLog entry with success status.
    - On failure:
      - Increment RetryCount.
      - If retries < max (e.g. 5), set Status = Pending (for retry).
      - Else:
        - Status = Failed, FailedAt = now.
      - Create NotificationDeliveryLog entry with failure status and error.

Channel senders:

- Email:
  - Use existing or new SMTP abstraction.
  - Take FromName / FromAddress from:
    - Tenant NotificationChannelConfig if set.
    - Otherwise global default.
- Sms:
  - Implement using an interface; the underlying provider can be stubbed but must be functional logically.
- InApp:
  - For now, at minimum:
    - Represent in-app notifications via:
      - NotificationDeliveryLog plus endpoint(s) to list them for a user.
    - Do NOT leave this unimplemented or empty.
- Webhook:
  - Send HTTP request to the target URL.
  - Include HMAC signature header using a secret linked to tenant or event (as appropriate).
  - Log status and body.

Make sender idempotent:
- If a given OutboxItem is accidentally processed twice, avoid double-sending where possible (e.g. by checking Status or using delivery log / idempotency key per provider).

Step 5: Tenant Notification APIs – `/api/tenant/notification/*`
--------------------------------------------------

Base path: `/api/tenant/notification`

All endpoints:

- Are tenant scoped (TenantId from token).
- Require appropriate tenant admin roles (e.g., TenantAdmin, SecurityOfficer, ComplianceOfficer where relevant).

Template API

- `GET /api/tenant/notification/templates`
  - Returns list of NotificationTemplateDto (tenant-specific plus indicator if overriding global).

- `GET /api/tenant/notification/templates/{id}`
  - Returns NotificationTemplateDto including localizations.

- `POST /api/tenant/notification/templates`
  - Body: CreateNotificationTemplateRequest:
    - EventType
    - IsEnabled
    - Localizations (language, subject, html, text).

- `PUT /api/tenant/notification/templates/{id}`
  - Body: UpdateNotificationTemplateRequest.

- `DELETE /api/tenant/notification/templates/{id}`
  - Deletes tenant override. Global default remains.

ChannelConfig API

- `GET /api/tenant/notification/channels`
  - Returns NotificationChannelConfigDto for current tenant.
  - If none yet, returns default from global config.

- `PUT /api/tenant/notification/channels`
  - Body: UpdateNotificationChannelConfigRequest:
    - EmailEnabled, EmailFromName, EmailFromAddress
    - SmsEnabled, SmsSenderId
    - InAppEnabled
    - WebhookEnabled

Event Subscription API

- `GET /api/tenant/notification/events`
  - Returns list of NotificationEventSubscriptionDto for known event types, including:
    - EventType
    - Description (code or key).
    - DefaultChannels.
    - OverrideUserPreference.

- `PUT /api/tenant/notification/events/{eventType}`
  - Body: UpdateNotificationEventSubscriptionRequest:
    - DefaultChannels
    - OverrideUserPreference

Logs API

- `GET /api/tenant/notification/logs`
  - Query parameters:
    - eventType (optional)
    - channel (optional)
    - status (optional)
    - recipient (optional, substring search)
    - from / to (optional date range)
    - paging parameters
  - Returns paged NotificationDeliveryLogDto with:
    - EventType
    - Channel
    - Status
    - RecipientMasked (email/phone partially masked)
    - Timestamp
    - ProviderResponseCode (short).

All responses must use your standard API envelope and error conventions.

Step 8: Cross-cutting – localization, privacy, performance
--------------------------------------------------

Localization

- All new Admin Portal texts must be defined via i18n keys.
- EventType and Event descriptions should be localizable (do not hardcode “Security.NewLogin” descriptions directly).

Privacy

- In logs:
  - Mask recipient emails:
    - e.g., `user***@domain.com`.
  - Mask phone numbers:
    - e.g., `+98******1234`.
- No secret keys, provider tokens, or full raw payloads should be visible in UI logs.

Performance & Reliability

- Outbox queries:
  - Use paging, indexes and limit batch size in ProcessPendingAsync.
- Retry strategy:
  - Distinguish between transient and permanent errors if possible:
    - 5xx or timeouts → retry.
    - 4xx like invalid address → mark as Failed without further retries.
- Make sure background processing does not deadlock or block main request threads.

Developer Experience

- INotificationRouter:
  - Provide a simple, well-documented interface for other modules to use.
  - All modules should call the router with a `NotificationEventContext` instead of constructing outbox records themselves.
- Keep NotificationCenter independent from specific SMTP/SMS providers:
  - Use abstractions so provider-specific code can be swapped.
