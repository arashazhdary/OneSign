Step 4: Domain services

Implement IDeveloperOnboardingService

- Responsible for:
  - Creating a DeveloperAccount for a given user if not exist.
  - Managing DeveloperTenantAccess per tenant.

Methods example:
- EnsureDeveloperAccountForUserAsync(userId, email, displayName)
- GrantAccessAsync(developerId, tenantId, permissions)
- RevokeAccessAsync(developerId, tenantId)
- GetDeveloperTenantsAsync(userId)

Implement IIntegrationApplicationService

- Responsible for integration facing app management:
  - Creating IntegrationApplication and underlying ApplicationClient.
  - Updating IntegrationApplication and syncing ApplicationClient configuration.
  - Rotating client secret.

Methods example:
- CreateApplicationAsync(tenantId, CreateIntegrationApplicationRequest)
- UpdateApplicationAsync(appId, UpdateIntegrationApplicationRequest)
- DeleteApplicationAsync(appId) - optional if allowed
- RotateSecretAsync(appId) - returns new clientSecret once
- GetForTenantAsync(tenantId)
- GetDetailsAsync(appId)

When creating an app:
- Also create ApplicationClient in the Applications module with:
  - clientId
  - clientSecret
  - redirectUris
  - allowedGrantTypes (Authorization Code + PKCE at least)
  - default scopes

Implement IApiKeyService

- Responsible for:
  - Generating secure API keys.
  - Hashing and storing them.
  - Validating keys for authentication.

Methods example:
- CreateApiKeyAsync(tenantId, serviceAccountId, CreateApiKeyRequest)
  - Generate a cryptographically strong random key string.
  - Hash it (for example using HMAC or a strong hash).
  - Store hash in ApiKeyEntity.
  - Return the plain key once.
- RevokeApiKeyAsync(apiKeyId)
- ValidateApiKeyAsync(plainKey)
  - Return tenantId and serviceAccountId when valid, or null if invalid or revoked.

Implement IWebhookEndpointService

- CRUD for WebhookEndpoint
- In this phase, focus on data model and configuration.
- Actual event delivery can be a later phase, but configuration must be fully functional.

Implement Token Debug service

- A service used by DebugTokenCommand:
  - Accept a JWT token.
  - Decode header and payload.
  - Validate signature using current signing keys from the Identity/Auth module.
  - Validate issuer, audience and expiry.
  - Extract claims like:
    - tenantId
    - clientId
    - scopes
  - Return TokenDebugResultDto with:
    - IsValidSignature
    - IsExpired
    - HeaderJson
    - PayloadJson
    - TenantId
    - ClientId
    - Scopes

Step 5: DevPortal API endpoints

All DevPortal endpoints must be under:

- `/api/devportal/...`

They must:
- Resolve current authenticated user.
- Resolve DeveloperAccount from that user.
- Check DeveloperTenantAccess for operations that require tenant context.
- Enforce permissions:
  - manage apps
  - manage api keys
  - view logs

Developer profile and tenant access

Endpoints:
- GET `/api/devportal/profile`
  - Returns DeveloperProfileDto.
- GET `/api/devportal/tenants-access`
  - Returns list of DeveloperTenantAccessDto.

Integration Applications

Endpoints:
- GET `/api/devportal/apps`
  - Query applications for the selected tenant in context.
- GET `/api/devportal/apps/{id}`
  - Get application details including underlying client info.
- POST `/api/devportal/apps`
  - CreateIntegrationApplicationRequest
  - Creates IntegrationApplication and ApplicationClient.
- PUT `/api/devportal/apps/{id}`
  - UpdateIntegrationApplicationRequest
- DELETE `/api/devportal/apps/{id}`
  - Optional - if allowed by business rules.
- POST `/api/devportal/apps/{id}/rotate-secret`
  - Rotates client secret, returns the new secret once in the response.

Logs for an app (integration with Observability module):

- GET `/api/devportal/apps/{id}/logs?take=50`
  - Returns recent AuditEventDto related to that clientId for the current tenant.
  - Use Observability module query service filtering by:
    - TenantId
    - TargetType = Application
    - TargetId or DataJson containing that clientId.

Service accounts and API keys

Service accounts endpoints:
- GET `/api/devportal/service-accounts`
- GET `/api/devportal/service-accounts/{id}`
- POST `/api/devportal/service-accounts`
  - CreateServiceAccountRequest:
    - Name
    - Description
    - AllowedScopes
- PUT `/api/devportal/service-accounts/{id}`
- DELETE `/api/devportal/service-accounts/{id}`

ApiKeys endpoints:
- GET `/api/devportal/api-keys`
  - List keys for current tenant, include:
    - ServiceAccount name
    - CreatedAt
    - ExpiresAt
    - Status
- POST `/api/devportal/service-accounts/{id}/api-keys`
  - CreateApiKeyRequest with optional expiration.
  - Returns ApiKeyDto + PlainKey once.
- POST `/api/devportal/api-keys/{id}/revoke`
  - Sets Status = Revoked.

Webhook endpoints

- GET `/api/devportal/webhooks`
- GET `/api/devportal/webhooks/{id}`
- POST `/api/devportal/webhooks`
  - CreateWebhookEndpointRequest
- PUT `/api/devportal/webhooks/{id}`
  - UpdateWebhookEndpointRequest
- DELETE `/api/devportal/webhooks/{id}`

Tools - Token debugger

- POST `/api/devportal/tools/token-debug`
  - Body: TokenDebugRequestDto with raw token.
  - Returns TokenDebugResultDto as described above.

Step 6: API key authentication

Implement API key based authentication for backend-to-backend integration.

- Add an authentication handler or middleware that:
  - Reads API key from a header such as `X-Onesign-ApiKey`.
  - Validates the key via IApiKeyService.ValidateApiKeyAsync.
  - If valid:
    - Sets a principal representing the service account.
    - Includes tenantId and serviceAccountId in claims or context.
  - If invalid:
    - Rejects with 401 Unauthorized.

Use this authentication scheme only for appropriate external API endpoints, not for internal admin or DevPortal endpoints.

Log all API key usage via IAuditWriter:
- Category = Integration
- Action = "ApiKey.Request"
- Include:
  - TenantId
  - ServiceAccountId
  - Path
  - Result status (success or failure)
