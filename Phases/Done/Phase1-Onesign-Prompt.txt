High level goals of Phase 1
According to the spec, Phase 1 must deliver a production grade Core SSO platform with:

- Multi tenant support in a single shared database, TenantId on all relevant entities
- Identity provider implementing OIDC Authorization Code plus PKCE
- Email plus password login and one social login (Google)
- Login Portal frontend for end users
- Admin Portal frontend for Global Admin and Tenant Admin
- User, Tenant, Application, Token and Audit basics
- Minimal but clean SDKs for .NET backend and React frontend
- Full multi language support end to end (at least English and Persian) from backend to frontend

Very important constraints
Read these carefully and respect them strictly.

1) Phase scope
- Do not implement any features that belong to later phases such as OrgUnit tree, delegated admin, ABAC, SCIM, SAML, per tenant database or advanced billing.
- Only implement what is clearly within Phase 1 scope in Phase1-Onesign-CoreSSO.md, but design the architecture so later phases can be added cleanly.

2) Architecture
- You must strictly follow the naming, folder structure, endpoints and DTO definitions in the Phase1-Onesign-CoreSSO.md file.
- The architecture must be a modular monolith, with modules like Tenants, Identity, Applications, Audit kept isolated at the Domain and Application layers.
- Multi tenancy must be correctly handled from day one: TenantId must be enforced in queries and tokens must always carry a clear tenant_id claim.

3) Multi language (critical requirement)
This system must be multi language ready from day one, across backend and frontends:

- Backend:
  - Do not hardcode user facing messages directly into controllers or services.
  - Introduce an internal localization mechanism (for example resource based or a simple IStringLocalizer abstraction) that can return messages in at least English and Persian.
  - Error and validation messages must be represented in a way that can be localized, either by:
    - returning message codes and letting the frontend map to localized text, or
    - using a backend localization layer to produce localized messages based on a requested culture.
  - All APIs that return user visible messages must consider a language or culture (for example from header, query string, or tenant preferences).

- Frontend (Login Portal and Admin Portal):
  - Integrate a proper i18n solution (for example a Next.js friendly i18n library) from the start.
  - All static texts in the UI must be localized through the i18n mechanism, not hardcoded strings.
  - The user must be able to see the UI in English and Persian at least.
  - Implement a simple but real mechanism to pick the language (tenant preference, user preference, or a toggle) and wire it through to backend calls when needed.

Do not treat multi language as "later". Design and implement it as a cross cutting concern in Phase 1.

4) No TODOs, no partial implementations (critical requirement)
- Do not leave any class or method with TODO, NotImplementedException, or empty bodies that are supposed to be implemented.
- If you introduce a class or method that is part of the Phase 1 design, implement it fully.
- If something is truly out of Phase 1 scope, do not create stub classes or methods for it. Just leave it for later phases and do not add dead code now.

5) Code quality
- Code must compile, be idiomatic, and be ready for real world use, not demo or toy quality.
- Implement proper validation, basic error handling and simple logging where needed.
- Security and multi tenant isolation take priority over shortcuts.

Step 6: OIDC flows and security
Implement a correct OIDC Authorization Code plus PKCE flow as described:

- Discovery endpoint returns valid OpenID config based on issuer and tenant routing.
- /connect/authorize validates:
  - client_id, redirect_uri, response_type, scope, state, code_challenge, code_challenge_method
  - tenant and application client
- If the user is not authenticated, redirect to Login Portal.
- After login success, create an authorization code, persist it and redirect back with code and state.
- /connect/token validates code and code_verifier, client and redirect_uri, and then issues:
  - access_token
  - id_token
- Tokens must be JWTs, sign them with a signing key and include at least:
  - sub, tenant_id, client_id
  - basic user info (subject, email) where appropriate.

Keep the implementation extensible for future features such as MFA, but do not implement those features now.
No security related method is allowed to be left as a TODO or stub.
