Step 3: Event to Webhook pipeline
--------------------------------------------------

Define an internal event mapping service:

- Interface:
  - `IExtensibilityEventMapper`
    - `ExtensibilityEvent? Map(object domainEvent)`

ExtensibilityEvent:
- EventType (string)
- TenantId
- PayloadJson (string)
- OccurredAt

Implement mapping for at least these domain events:

- User created, updated, deleted
- Login succeeded or failed
- Token issued or revoked
- AccessRequest approved or denied
- Lifecycle event executed

Make sure each mapping:

- Produces a stable EventType name:
  - "identity.user.created"
  - "auth.login.succeeded"
  - etc.
- Builds a payload with:
  - ids
  - relevant metadata
  - no sensitive secrets or credentials

Queueing:

- Introduce an internal queue or outbox table for Webhook deliveries if you already have one.
- For each ExtensibilityEvent:
  - Create Webhook delivery records for all subscriptions of that tenant which are enabled and subscribed to that EventType.

Webhook dispatcher:

- Service:
  - `IWebhookDispatcher` running as a background worker.

Behavior:

- For each pending delivery:
  - Build HTTP POST request:
    - URL = WebhookSubscription.EndpointUrl
    - Body = PayloadJson
    - Headers:
      - X-Onesign-EventType = EventType
      - X-Onesign-Timestamp = unix timestamp
      - X-Onesign-Signature = HMAC-SHA256(secret, timestamp + body) or similar
  - Handle responses:
    - If HTTP 2xx:
      - mark as success
    - If 4xx or 5xx or timeout:
      - schedule retry according to retry policy
      - after max attempts, mark as failed

Observability:

- Log and audit:
  - "Extensibility.WebhookDeliverySucceeded"
  - "Extensibility.WebhookDeliveryFailed"
- Add basic metrics per tenant if your metrics module is ready.

Step 4: Login hooks execution
--------------------------------------------------

Define execution service:

- `ILoginHooksExecutor`
  - `Task<LoginHookResult> ExecutePreLoginAsync(LoginHookContext context)`
  - `Task ExecutePostLoginAsync(LoginHookContext context)`

LoginHookContext should contain:

- TenantId
- UserId
- ClientId
- RiskScore (from IdentityInsights if available)
- Auth context (IP, userAgent, geo info if you already capture them)

LoginHookResult:

- Allow (bool)
- AdditionalClaims (dictionary or claim collection)
- ExtraFlags (for future use, for example requireExtraMfa etc)

Pre login integration:

- In auth pipeline, after successful credential validation and before final login decision:
  - Load all enabled LoginHooks for this tenant with Stage = PreLogin.
  - For each hook:
    - Call HTTP endpoint with context JSON body.
    - Enforce timeout = TimeoutSeconds.
    - Verify HMAC if you support incoming signatures.
    - Interpret response:
      - basic contract:
        - `allow` boolean
        - `additionalClaims` optional
        - `flags` optional
    - Combine results:
      - If any hook returns allow = false:
        - depending on FailBehavior:
          - if that hook is configured fail closed or this explicit deny, block login.
  - If blocked:
    - Stop login and emit audit event "Extensibility.LoginHookBlockedLogin".
  - If allowed:
    - merge AdditionalClaims into the claims for token issuance.

Post login integration:

- After successful login and token issuance:
  - queue execution for Stage = PostLogin hooks.
  - Fire and forget:
    - do not block response to user.
  - Use same context but include token id or correlation id if needed.

Fail behavior rules:

- For PreLogin:
  - Apply FailBehavior per hook as configured:
    - FailOpen:
      - ignore hook failure (log and continue).
    - FailClosed:
      - treat error like allow = false or error.
- For PostLogin:
  - Always fail open, errors must just be logged.

Step 5: Token transformation rules and engine
--------------------------------------------------

TokenTransformationRule storage:

- Already defined entity with RuleDefinition as JSON.

RuleDefinition:

- Use a simple JSON based DSL, for example:

  {
    "rules": [
      {
        "when": { "hasRole": "TenantAdmin" },
        "addClaims": { "is_admin": true }
      },
      {
        "mapRolesToClaim": "groups"
      },
      {
        "copyOrgUnitPathToClaim": "org_path"
      }
    ]
  }

You do not need a super complex DSL. Implement a minimal but real rule set:

- Conditions:
  - hasRole
- Actions:
  - addClaims (simple key value)
  - mapRolesToClaim (map role names to an array claim)
  - setClaimFromOrgUnitPath

Engine:

- Implement `ITokenTransformationEngine`:

  - `ClaimsPrincipal ApplyRules(ClaimsPrincipal principal, Guid tenantId, string clientId)`

Steps:

- Load all TokenTransformationRule records for tenant and client where Enabled = true, ordered by Order.
- For each rule:
  - Parse RuleDefinition once and cache if possible.
  - Apply rule on current claims.
- Return transformed ClaimsPrincipal.

Validation:

- When saving a rule via API:
  - Parse RuleDefinition.
  - If invalid, reject save with validation error.
- At runtime:
  - If a rule still fails parsing:
    - log error.
    - For now skip that rule and do not abort the whole issuance, unless config says otherwise.

Integration:

- In token issuance pipeline:
  - After building the default claims and before signing and issuing tokens:
    - call `ITokenTransformationEngine.ApplyRules`.
    - use returned claims for the token.

Audit:

- Optionally log aggregated event:
  - "Extensibility.TokenTransformationApplied" with rule count, not every claim change.
