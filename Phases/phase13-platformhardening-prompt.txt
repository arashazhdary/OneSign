Step 2: TenantStatus model and lifecycle enforcement
--------------------------------------------------

1) Extend Tenant domain and persistence model

- Add TenantStatus enum, for example:
  - Active
  - Suspended
  - Terminating
  - Terminated

- Add corresponding field in the Tenant entity and Tenant table.

- Ensure there is a default of Active for existing tenants.

2) Global admin API for tenant status

- In the Global Admin API layer (wherever you manage tenants globally), add:
  - `PUT /api/global/tenants/{id}/status`

- Request body:
  - NewStatus value.

- Implement strict transition validation:
  - Allowed:
    - Active -> Suspended
    - Suspended -> Active
    - Active -> Terminating
    - Suspended -> Terminating
    - Terminating -> Terminated
  - Disallowed transitions must be rejected with a clear error code.

- For every change:
  - Write audit events, for example:
    - "Tenant.StatusChanged" with from and to values and actor id.

3) TenantStatus enforcement middleware

- Create a middleware or pipeline component that runs on every tenant scoped API request.

- Responsibilities:
  - Resolve TenantId from the context (host name, path, token, or existing tenant resolution pipeline).
  - Load TenantStatus (using cached TenantConfig if available).
  - If TenantStatus is:
    - Active: allow.
    - Suspended:
      - Block interactive login, token issuance and most tenant APIs.
      - Return 403 or a tenant suspended error code.
    - Terminating or Terminated:
      - Block all tenant facing APIs.
      - Optionally return 404 to avoid leaking details about terminated tenants.

- Exception list:
  - GlobalAdmin and internal platform APIs must still function in order to manage status, migrations and restore.

- Make sure enforcement is consistent across:
  - Login and token endpoints.
  - Admin Portal tenant APIs.
  - DevPortal tenant APIs.
  - Account Center APIs.

Step 3: Data topology and TenantDbConnectionFactory
--------------------------------------------------

1) Extend TenantConfig

- Add fields:
  - DataIsolationMode:
    - SharedDatabase
    - DedicatedDatabase
  - DedicatedConnectionStringName or DedicatedConnectionString
    - Choose a pattern consistent with your configuration system.

2) TenantDbConnectionFactory

- Define an interface such as:
  - `ITenantDbConnectionFactory` with method:
    - `string GetConnectionString(Guid tenantId)`

- Implementation:

  - Load TenantConfig:
    - Use caching (see Step 5) to avoid frequent DB hits.
  - If DataIsolationMode is SharedDatabase:
    - Return the main shared database connection string.
  - If DataIsolationMode is DedicatedDatabase:
    - Return the dedicated connection string for this tenant.

- Provide convenience methods as needed:
  - For example:
    - `Task<DbConnection> CreateOpenConnectionAsync(Guid tenantId)` if your architecture prefers that.

3) EF Core integration

- Integrate TenantDbConnectionFactory into DbContext creation.

- Pattern example:
  - Use a DbContextFactory or per request DbContext injection that:
    - Resolves TenantId from the current context.
    - Asks ITenantDbConnectionFactory for the connection string.
    - Configures DbContextOptions with that connection string.

- Make sure:
  - Migrations still apply correctly.
  - Connection lifetime and pooling are handled according to best practices.
  - You do not break multi tenant query filters.

Step 4: Migration tool - Shared to Dedicated database
--------------------------------------------------

Implement a migration tool (CLI or internal command) for tenant data.

1) High level behavior

- Input:
  - TenantId
  - TargetConnectionString (for dedicated database) or connection key.

- Steps:
  1. Mark tenant status as Terminating or a maintenance state.
  2. Copy all rows for TenantId from shared database to the new dedicated database.
     - This requires awareness of all tenant scoped tables.
  3. Update TenantConfig:
     - DataIsolationMode = DedicatedDatabase
     - DedicatedConnectionStringName or value set to the target.
  4. Optionally clean up tenant data from the shared DB once you are certain migration succeeded.
  5. Set tenant status back to Active.

- All steps must be logged and audited:
  - "Tenant.MigrationStarted"
  - "Tenant.MigrationCompleted"
  - "Tenant.MigrationFailed"

2) Implementation details

- Implement as:
  - A console application within the solution, or
  - A background job runner or admin only endpoint that triggers the migration process.

- Ensure:
  - The tool is idempotent or at least safe to rerun after partial failure.
  - Errors are clearly reported.

- Do not leave the migration pipeline half implemented.
  - If a step is not in scope, do not scaffold it.

Step 5: Caching TenantConfig and client configuration
--------------------------------------------------

1) TenantConfig cache

- Implement a caching layer for TenantConfig lookups.

- Requirements:
  - In memory cache for local speed.
  - Optional distributed cache (Redis or similar) if you are running multiple nodes.

- API:
  - Something like `ITenantConfigProvider`:
    - `Task<TenantConfig> GetTenantConfigAsync(Guid tenantId)`
  - Internal behavior:
    - Use cache with a TTL.
    - Invalidate or update cache when TenantConfig is changed through admin APIs.

2) ClientConfig cache

- For OIDC and API clients:
  - Implement caching for client configuration similar to TenantConfig.

- Ensure:
  - ClientId to configuration mapping is cached.
  - Cache invalidation happens when new clients are added or updated.

3) Metrics

- Integrate with Observability (Phase 6):
  - Expose cache hit and miss metrics for TenantConfig and client configuration.

Step 6: Rate limiting and throttling
--------------------------------------------------

1) Design

- Implement rate limiting at the API gateway or API layer per:
  - TenantId
  - ClientId (OIDC client)
- Rate limits must be plan aware:
  - Use Billing module to get plan caps per tenant.

2) Implementation

- Introduce a rate limiting middleware or filter in the API pipeline.

- Behavior:
  - For each request:
    - Identify TenantId and optionally ClientId.
    - Determine the allowed rate based on the tenant plan:
      - Basic, Pro, Enterprise, etc.
    - Track request counts in a time window (sliding or fixed).
    - If limit exceeded:
      - Return HTTP 429 Too Many Requests.
      - Include an error code and optional retry-after header.

- Storage:
  - Use an appropriate store for counters:
    - In memory for single node.
    - Distributed store for multi node (Redis or similar).

3) Observability

- Expose metrics:
  - Per tenant and per client request counts.
  - Rate limit hits.
- Log events when:
  - Rate limiting is triggered.
